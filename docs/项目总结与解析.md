# 项目总结与解析

## 1. 项目目标

该仓库实现了一个面向课程项目的自动驾驶最小闭环系统：
- Unity 负责环境仿真与传感器生成。
- ROS 侧完成传感器接入、感知建图、红绿灯识别、行为决策与车辆控制。
- 控制指令再回传 Unity，形成闭环验证。

从工程形态看，这是一个典型的多包 catkin 工作区，偏“集成验证”而非“生产级模块化”。

## 2. 模块级解析

### 2.1 simulation（仿真通信桥）

核心节点：
- `JSON_param_reader`：读取 `simulation_config.json`，把 `controlConfig/sensorConfig` 写入 ROS 参数。
- `unity_TCP_stream_receiver`：监听 TCP 数据流并分发解析器（真值状态、IMU、RGB、Depth）。
- `ROS_command_transmitter`：订阅 `car_command`，100Hz 通过 UDP 发送 4 通道控制量。

关键点：
- 状态解析器会发布 `world -> OurCar/INS` TF。
- 深度图在 ROS 侧发布为 `16UC1`，供 `depth_image_proc` 使用。
- `simulation.launch` 会直接启动 Unity 可执行文件。

### 2.2 perception（建图链路）

由两段 launch 组成：
- `perception.launch`：
  - 发布车体到各相机的静态 TF；
  - 运行 nodelet 管理器与 `depth_image_proc/point_cloud_xyz`，生成 `/depth/points`。
- `octomap.launch`：
  - 运行 `octomap_server`，输入 `/depth/points`；
  - 开启 2D 投影，输出 `/projected_map`。

关键点：
- 框架中同时保留了 C++ 静态 TF 节点与 launch 静态 TF 方案，实际主流程使用 launch 方案。

### 2.3 traffic_light_detector（红绿灯识别）

三阶段流水线：
1. `semantic_depth_median_node`：在语义图中提取类别 215 的连通域，映射到深度图并估计距离中值；
2. `traffic_light_detection`：把深度视角 bbox 投影到左 RGB 相机平面；
3. `color_detector_node`：在 ROI 内进行 HSV 统计，发布 `traffic_light_color`。

消息类型：
- `TrafficLightBBox`
- `TrafficLightBBoxArray`
- `TrafficLightColor`

### 2.4 decision_making（行为决策）

`decision_making_node` 订阅 `traffic_light_color`，输出 `traffic_decision`：
- `red -> BRAKE`
- `yellow -> ACCELERATE`
- `green -> DRIVE`
- 超时（1s）默认 `DRIVE`

### 2.5 dummy_controller（控制器）

`dummy_controller_node` 实际是 PID 路径跟踪控制器：
- 输入：`/move_base_simple/goal`、车辆姿态/速度、`traffic_decision`；
- 输出：`car_command`；
- 额外输出：`/reached_goal`（用于目标点串行发布）。

控制逻辑：
- 距离误差做油门 PID；
- 航向误差做转角 PID；
- 若 `traffic_decision == BRAKE`，强制刹车覆盖。

### 2.6 path_recorder（轨迹工具）

提供多节点：
- `path_publisher_node`：按里程阈值记录轨迹并写 CSV；
- `csv_goal_publisher`：从 CSV 顺序发布目标点；
- `show_path_node` / `showpoints`：用于路径可视化。

现状是“工具集合”，节点之间数据格式和路径配置存在不统一。

## 3. 端到端流程总结

1. Unity 产生图像、姿态、速度等流数据；
2. `simulation` 包将其转成 ROS 消息和 TF；
3. `traffic_light_detector` 输出红绿灯状态；
4. `decision_making` 生成驾驶策略；
5. `dummy_controller` 将路径跟踪与交通决策融合为 `car_command`；
6. `ROS_command_transmitter` 把控制量回传 Unity；
7. `perception` 可并行产出 `/projected_map` 供规划模块使用。

## 4. 工程现状评估

优点：
- 主链路闭环完整，覆盖“感知-决策-控制-回环”。
- 模块边界清晰，基本以 topic 解耦。
- 可运行资产完整（包含 Unity build 与 ROS 包）。

主要问题：
- 存在较多硬编码绝对路径（CSV、地图导出路径等），可移植性弱。
- 部分 README 与源码行为不完全一致（历史内容残留）。
- `path_recorder` 工具节点对 CSV 列定义不统一，容易用错。
- `decision_making`、`dummy_controller` 的参数多为硬编码，调参与复现实验成本偏高。

## 5. 建议的下一步重构方向

1. 参数化改造：把路径、阈值、PID 系数、超时阈值统一放到 ROS 参数或 YAML。
2. 统一数据协议：明确 `recorded_path.csv` 的唯一字段规范，并让所有工具复用同一解析器。
3. 启动编排：新增顶层 `bringup.launch`，一键拉起常用模块组合。
4. 健壮性增强：为关键节点增加输入有效性校验和异常日志（例如空图像、空 bbox、异常深度）。
5. 测试与回放：补充 rosbag 回放脚本，建立最小回归测试流程。

## 6. 结论

该项目已经具备课程级自动驾驶系统的核心闭环能力，适合作为后续优化和实验平台。若要提升到长期维护的工程形态，重点应放在“参数化、协议统一、启动标准化、自动化验证”四个方向。
